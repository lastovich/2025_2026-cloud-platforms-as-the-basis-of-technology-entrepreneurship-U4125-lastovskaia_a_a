## Разработка инфраструктуры MVP AI приложения

### AI-ассистент “Ничто не забыто”  
Приложение, которое помогает человеку снизить стресс от "внезапно" навалившихся дел:
- продление документов (паспорта, визы, страховки)
- контроль подписок (Netflix, SaaS, спортзал)
- договоры (аренда, кредиты)
- регулярные задачи (налоги, медосмотры)

AI-функции:
- извлечение данных из документов 
- автоматическое определение сроков действия
- умные напоминания 
- чат-интерфейс
### Stage 1 — MVP (до 500 пользователей/день)

#### Пользователь
- регистрация и авторизация  
- просмотр личного кабинета  


#### Внутренняя подписка (бесплатный тариф с ограничениями)
- до 3 документов  
- до 3 подписок  

#### Документы
- загрузка документов (PDF, изображения)  
- хранение метаданных (дата истечения, тип)  

#### Подписки
- добавление внешних подписок (например, Netflix, аренда)  
- контроль сроков оплаты и продления  

#### Уведомления
- push-уведомления о скором окончании подписок  
- еженедельные напоминания  

##### Общая архитектура (логика потоков)

- Пользователь отправляет запрос с мобильного приложения  
- Cloud Run (монолит) обрабатывает запрос  
- Данные сохраняются в Cloud SQL  
- Файлы загружаются в Cloud Storage  
- Cloud Scheduler запускает проверку событий  
- Cloud Tasks передаёт задачи уведомлений  
- Firebase Cloud Messaging отправляет push-уведомления на устройство

### Обоснование 
### Cloud Run → Google Kubernetes Engine (GKE)

**Этап 1–2: Cloud Run**

На начальных этапах выбран Cloud Run, так как:
- минимальные затраты при низкой нагрузке (оплата за фактическое использование)
- отсутствие необходимости управлять инфраструктурой (снижение операционных расходов)
- высокая скорость разработки и вывода продукта на рынок (time-to-market)
- автоматическое масштабирование без настройки DevOps

С точки зрения бизнеса это позволяет:
- протестировать гипотезу продукта с минимальными инвестициями
- избежать затрат на избыточную инфраструктуру
- быстро вносить изменения в продукт

**Этап 3: переход на GKE**

При росте до 10 000+ пользователей Cloud Run становится менее экономически ффективным.
Переход на GKE обоснован:
- снижением стоимости при стабильной высокой нагрузке
- возможностью тонкой настройки ресурсов (CPU, memory)
- поддержкой микросервисной архитектуры
- лучшим контролем SLA и отказоустойчивости

### Pub/Sub

На раннем этапе система использует синхронные вызовы, что упрощает разработку.
Внедрение Pub/Sub при повышении загрузки системы решает задачи:
- повышения устойчивости 
- возможность обрабатывать рост нагрузки без переписывания логики
- снижение рисков отказов при масштабировании

### BigQuery
На ранних этапах аналитика либо отсутствует, либо реализуется в основной базе данных.
Использование BigQuery позволяет:
- обрабатывать большие объёмы данных без нагрузки на основную БД
- выполнять быстрые аналитические запросы
- строить отчёты и прогнозы

### API Gateway (Apigee)
На ранних этапах клиенты напрямую обращаются к backend-сервисам.
При масштабировании:
- увеличивается количество сервисов
- усложняется управление API
- появляются требования к безопасности и контролю доступа

Введение API Gateway (Apigee) позволяет:
- централизовать управление API
- реализовать контроль доступа, лимиты и мониторинг
- упростить интеграцию с внешними системами
